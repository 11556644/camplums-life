有，而且我会把“可演示”定义成：**不是功能堆砌，而是能让观众在 8–15 分钟内看懂这个平台如何完成一次真实校园服务闭环**。因为这是高校数字校园场景，Demo 最低也该体现统一身份、角色分工、流程留痕和后台管理，而不只是几张静态原型图。 [moe.gov](http://www.moe.gov.cn/srcsite/A16/s3342/202103/W020210322388403183703.doc)

另外，既然项目涉及学生数据，Demo 里也应该默认展示脱敏后的手机号、宿舍位置和操作日志，而不是为了“演示方便”把敏感信息全裸露出来。 [celtsc](http://www.celtsc.org/upload_files/file/20221019/1666146393257079276.pdf)

## 可演示标准

我脑子里的“可演示”，不是“页面能点”，而是满足 6 个标准：

- 能讲清一个用户故事：谁发起、谁响应、谁交付、谁确认、谁兜底。
- 能走通一个完整闭环：从登录/认证，到下单/履约，到评价/结算/归档。
- 能看到真实状态变化：不是跳页，而是订单状态、柜格状态、库存状态、信用分真的变化。
- 能体现平台底座：至少让人看到用户体系、交易体系、消息通知、风控/日志、后台。
- 能演一条异常支线：例如超时未取、教材破损、跑腿爽约，不然观众会觉得只是 Happy Path PPT。
- 能控制节奏：每条业务线最好 3–4 分钟讲完，避免细节过多把核心价值讲散。

如果更严格一点，我会把“可演示”拆成三层：

| 层级 | 标准 | 通过表现 |
|---|---|---|
| L1 | 可看懂 | 观众 1 分钟内知道这条业务线解决什么问题 |
| L2 | 可走通 | 至少 1 个主流程完整闭环，状态真实变化 |
| L3 | 可相信 | 有日志、后台、异常处理、权限/隐私展示，像真系统 |

## 三条业务线标准

我会给三条业务线分别设“最小 Demo 合格线”。

| 业务线 | Demo 合格线 | 最佳展示点 |
|---|---|---|
| 智能柜 | 完成“发布商品 -> 下单 -> 绑定柜格 -> 卖家存入 -> 买家取件 -> 确认收货” | 柜格状态变化、动态取件码、远程开柜、日志追踪 |
| 教材订阅 | 完成“选学期教材 -> 支付押金/订阅 -> 分配教材 -> 领取 -> 归还 -> 质检 -> 再上架” | 单本教材的生命周期可视化 |
| 自由市场 | 完成“发布任务/商品 -> 接单/报价 -> 交付 -> 评价 -> 纠纷处理” | 楼长角色、信用变化、仲裁流程 |

我理想里的要求不是“每条都很深”，而是“每条都能证明一件事”：

- 智能柜证明：平台能把线下交接标准化、异步化。
- 教材订阅证明：平台不只是交易，还能管理循环资产。
- 自由市场证明：平台能承载校园内的人力服务网络，而不是只有二手买卖。

## 理想演示场景

我脑子里最理想的 Demo Day，不是三套分裂的系统，而是**同一个校园生活服务平台，切 3 个场景**。观众始终感觉：底座是同一个，账号是同一个，订单是同一个，只是履约方式不同。

### 开场画面

第一屏不是登录页，而是一个很清晰的首页：

- 顶部：学校名、当前身份、消息提醒、信用分。
- 中间：三个入口卡片  
  - 智能柜闲置交易  
  - 教材订阅  
  - 自由市场 / 技能互换
- 底部：最近订单、待办提醒、运营公告。

这样观众第一眼就知道：这不是单点工具，而是平台。

### 我理想中的角色设定

为了演示顺滑，我会预置 6 个账号：

- 学生 A：卖家 / 普通用户
- 学生 B：买家 / 订阅用户
- 学生 C：跑腿服务者
- 楼长 D：楼栋运营角色
- 教务 E：教材管理员
- 平台管理员 F：总后台

最好支持“一键切换演示身份”，否则 Demo Day 会浪费大量时间在重新登录。

## Demo Day 流程

下面是我脑子里比较理想的一套 12–15 分钟脚本。

| 时间 | 画面 | 操作 | 观众看到什么 |
|---|---|---|---|
| 0:00–1:00 | 平台首页 | 主讲人介绍平台定位 | 同一底座承载三条业务线 |
| 1:00–4:30 | 智能柜场景 | 学生 A 发布耳机，学生 B 下单，A 存柜，B 取件 | 异步交付闭环 |
| 4:30–8:00 | 教材订阅场景 | 学生 B 订阅“教材”，分配教材，学期末归还 | 教材循环资产流转 |
| 8:00–11:00 | 自由市场场景 | 学生 A 发布“代取快递”任务，学生 C 接单，楼长 D 协调交付 | 人力服务网络与信用体系 |
| 11:00–13:00 | 异常处理 | 演示一次超时/拒收/投诉 | 平台不是只有顺利路径 |
| 13:00–15:00 | 管理后台 | 切到运营后台和数据看板 | 能管、能查、能审计 |

### 第一段：智能柜闭环

这是最适合“炸场”的，因为最直观。

1. 学生 A 打开“发布闲置”，发一个二手耳机。  
   - 页面看到：标题、价格、成色、模糊位置“X 宿舍楼”、支持“智能柜交付”。

2. 学生 B 在商品流里看到并下单。  
   - 页面看到：订单状态从“待支付”到“待卖家交付”。

3. 学生 A 进入订单详情，点“申请智能柜交付”。  
   - 页面看到：附近柜机列表、可用柜格、预估保留时间。

4. 系统绑定柜格后，进入“去存放”。  
   - 页面看到：柜格编号、一次性开柜按钮、倒计时。

5. 模拟柜机端画面。  
   - 页面看到：柜门打开、卖家放入、拍照回传、柜门关闭、柜格状态切到“待买家取件”。

6. 学生 B 收到消息。  
   - 页面看到：站内信/短信提醒、动态取件码、柜机位置。

7. 学生 B 到柜机扫码开柜取件。  
   - 页面看到：验证码校验成功、柜门打开、订单状态变为“待确认收货”。

8. 学生 B 点击“确认收货并评价”。  
   - 页面看到：交易完成、信用分轻微上涨、日志形成闭环。

这一段的关键不是“柜子会开”，而是让观众看到 4 条状态同时变化：

- 订单状态变了。
- 柜格状态变了。
- 消息通知发了。
- 后台日志记录下来了。

### 第二段：教材订阅闭环

这段最适合展示“平台的第二增长曲线”，因为它证明你不是只能做二手交易。

1. 学生 B 进入“教材订阅”。  
   - 页面看到：按院系/学期推荐教材包，比如“计算机学院 2026 春季学期”。

2. 点开套餐详情。  
   - 页面看到：课程列表、教材版本、原价合计、订阅价、押金、权益说明。

3. 学生 B 下单。  
   - 页面看到：订单类型不是普通商品单，而是“订阅单”；支付结构显示“订阅费 + 可退押金”。

4. 后台自动分配教材副本。  
   - 页面看到：每本书都有唯一编号、当前状态“待领取”。

5. 切到“我的教材”。  
   - 页面看到：教材列表、领取方式（智能柜 / 楼长 / 服务点）、领取码。

6. 模拟时间推进到学期末，点击“归还”。  
   - 页面看到：归还预约、归还点选择、待归还清单。

7. 教材管理员完成质检。  
   - 页面看到：成色评级从“良好”更新、是否扣损耗费、是否进入消毒。

8. 消毒完成后重新上架。  
   - 页面看到：同一本教材副本重新回到“可借”库存。

这条线最重要的演示点，不是支付，而是**“一本书的一生”**：

- 被版本库定义。
- 被引用。
- 被学生订阅。
- 被分配。
- 被归还质检。
- 被重新上架。

只要这个生命周期清楚，观众就会立刻明白“循环资产”这个模型成立。

### 第三段：自由市场闭环

这段用来证明平台的网络效应。

1. 学生 A 发布任务：“今晚 7 点前代取快递送到 3 号楼”，或者商品。  
   - 页面看到：预算、截止时间、模糊位置、仅限本楼可接。

2. 学生 C 作为服务者接单或报价。  
   - 页面看到：服务者等级、完成率、历史评价。

3. 学生 A 选择服务者。  
   - 页面看到：订单建立，联系方式仍然脱敏，只显示虚拟号码或站内聊天。

4. 服务中状态变化。  
   - 页面看到：待接单 -> 已接单 -> 服务中 -> 待确认完成。


6. 学生 A 确认完成并评价。  
   - 页面看到：服务者完成率提升，等级条变化，任务归档。

7. 再补一个小异常：学生 A 点“服务不符，发起申诉”。  
   - 页面看到：投诉单生成，楼长初审，平台仲裁入口出现。

这段最好的效果，是让观众意识到：

- 这不是传统外卖跑腿平台。
- 这是一个校内可信关系网络。
- “楼长”不是管理员，而是半运营、半信用增强节点。

## 每一步该看到什么

如果你问我 Demo 做到什么程度才“有说服力”，我的答案是：**每一步都必须有视觉上的反馈证据**，不能靠嘴讲。

### 用户前台必须看到

- 当前角色是谁。
- 当前可执行动作是什么。
- 当前订单/教材/任务处于什么状态。
- 下一步系统会发生什么。
- 隐私是怎么被保护的，比如手机号脱敏、宿舍号隐藏。 [celtsc](http://www.celtsc.org/upload_files/file/20221019/1666146393257079276.pdf)

### 运营后台必须看到

- 新增订单或订阅单。
- 柜格/库存/任务状态同步变化。
- 异常事件被记录。
- 用户信用分或履约记录更新。
- 管理员可以介入，而不是只能旁观。

### 最好加上的“演示增强件”

- 顶部全局消息中心：刚刚发生的事件实时弹出。
- 状态时间线：让观众看见这单是怎么一步步走完的。
- 统一事件日志：证明三条业务线真的是同一个底座。
- 数据看板实时数字跳动：比如“今日完成订单 +1”“柜格使用率更新”。

## 我会怎么判定这个 Demo 成功

我会用下面这套标准来验收 Demo Day，而不是“主讲人讲得顺不顺”。

- 观众能不能在前 90 秒内理解平台定位。
- 每条业务线能不能在 3–4 分钟内走完一个闭环。
- 状态变化是不是肉眼可见，而不是靠讲解补充。
- 异常处理有没有被证明，不是只演顺利路径。
- 三条业务线看起来是不是一个平台，而不是三个拼接项目。
- 后台、日志、风控、隐私有没有露出，证明这个系统不是“只会做前端页面”。

如果是我来定义一句最硬的验收标准，那就是：

> **Demo Day 结束时，观众应该能复述出：这个平台如何让校园里的“物品、教材、任务”都通过同一套交易底座流转起来。**

这就是我理想中的“可演示”标准，也是我脑子里最完整的一套 Demo Day 场景。
