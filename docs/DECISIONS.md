# 决策日志 (Decision Log)

> 每个重要决策必须记录：决策内容、理由、替代方案、风险、可回滚性

---

## D-001: 技术框架选择 — Next.js + TypeScript

- **日期**: 2026-05-22
- **决策**: 使用 Next.js 15 (App Router) + TypeScript 作为唯一技术框架
- **理由**:
  - 前后端一体，不需要独立后端服务
  - API Routes 直接写在同一项目，开发效率最高
  - SSR/SSG 可选，原型阶段用 CSR 即可
  - 生态成熟，shadcn/ui 等组件库完善
- **替代方案**:
  - React + Express (前后端分离) → 多一层部署复杂度，两天不够
  - Vue + Nuxt → 生态不如 Next.js 丰富
  - 纯 HTML + jQuery → 无类型安全，代码难维护
- **风险**: 低
- **可回滚**: 否（基础框架不可回滚）

## D-002: 数据库选择 — PostgreSQL（已从 SQLite 迁移）

- **日期**: 2026-05-22（初始 SQLite）→ 2026-05-23（迁移到 PostgreSQL 16）
- **决策**: 使用 PostgreSQL 16 + Prisma ORM（嵌入式二进制，随项目安装）
- **理由**:
  - SQLite 不支持并发写入，多人同时操作会锁死
  - PostgreSQL 支持真正并发（MVCC）、全文搜索、JSON 字段
  - 生产环境可直接使用，无需二次迁移
  - 嵌入式安装在 `~/.campus-pg/`，无需系统级安装
- **迁移方式**: `scripts/db-start.js` 自动下载 + 初始化 + seed
- **替代方案**:
  - SQLite（原方案）→ 并发瓶颈，已弃用
  - 云数据库（Neon/Supabase）→ 需要网络
- **风险**: 低
- **可回滚**: 是（改回 `provider = "sqlite"` 即可）

## D-003: UI 方案 — Tailwind CSS + shadcn/ui

- **日期**: 2026-05-22
- **决策**: Tailwind CSS + shadcn/ui 组件库
- **理由**:
  - shadcn/ui 组件复制到项目内，完全可控
  - 表格、表单、弹窗、卡片等组件现成可用
  - 两天时间内不需要手写任何基础 UI
- **替代方案**:
  - Ant Design → 包体积大，定制性差
  - MUI → 样式系统复杂
  - 纯 Tailwind → 基础组件需要手写，耗时
- **风险**: 低
- **可回滚**: 是（纯 CSS 仍可用）

## D-004: 认证方案 — 自建 JWT

- **日期**: 2026-05-22
- **决策**: 使用 jose 库自建 JWT 认证，不使用 NextAuth
- **理由**:
  - NextAuth 配置复杂，对接 Credentials Provider 有坑
  - 自建 JWT 逻辑简单，完全可控
  - 毕设不需要 OAuth 社交登录
- **替代方案**:
  - NextAuth.js → 配置成本高，调试时间不可控
  - Clerk/Auth0 → 外部服务依赖
- **风险**: 低（JWT 是成熟方案）
- **可回滚**: 是（认证模块独立）

## D-005: 支付方案 — 模拟支付

- **日期**: 2026-05-22
- **决策**: 使用模拟支付，完整流程但非真实接口
- **理由**:
  - 微信/支付宝真实接入需要企业资质 + 商户号（审核 3-7 天）
  - 学生毕设没有企业资质
  - 模拟支付走完整状态机流程，演示效果等同真实
- **替代方案**:
  - 真实微信/支付宝 → 需要营业执照，时间不可行
  - 沙箱环境 → 支付宝沙箱可用但微信沙箱需企业资质
- **风险**: 低（模拟支付本身极简）
- **可回滚**: 是（未来可替换为真实支付接口）

## D-006: 架构模式 — 单体模块化

- **日期**: 2026-05-22
- **决策**: 单体应用，按模块隔离，不拆微服务
- **理由**:
  - 两天时间不可能做微服务
  - 模块化单体通过 service 层隔离，满足 CLAUDE.md "跨服务交互通过 API" 的约束
  - 模块间通过 service 层调用，禁止跨模块直接查表
- **与 CLAUDE.md 的关系**:
  - CLAUDE.md 要求"至少抽出统一的用户/订单/支付/消息/信用服务"
  - 原型阶段以模块 (module) 代替服务 (service)，代码边界清晰
  - 未来可物理拆分为独立服务
- **风险**: 中（模块边界需要严格遵守，否则会退化为大泥球）
- **可回滚**: 是（模块化单体可随时拆分）

## D-008: 虚拟实体策略 — 预置数据，非功能模块

- **日期**: 2026-05-22
- **决策**: 教材、智能柜、柜格作为预置种子数据存在，不是独立功能模块
- **理由**:
  - 用户明确"实体物品虚拟存在"是数据层面的假设，不是要单独做一个"虚拟化功能"
  - 教材预置 15 种（含 ISBN、书名、成色、编号），系统当真实库存处理
  - 智能柜预置若干台 + 每台若干柜格，系统当真实硬件处理
  - 物流信息用前端定时器循环模拟 A→B→C→A
- **影响**: 种子数据脚本是 Phase 1 的核心产出，所有后续业务线依赖这些数据
- **可回滚**: 是（重置种子数据即可）

## D-009: Next.js 版本降级至 15

- **日期**: 2026-05-22
- **决策**: 从 Next.js 16 降级到 Next.js 15
- **理由**:
  - Next.js 16 默认使用 Turbopack，不支持中文路径（项目目录名为"校园生活"）
  - Next.js 15 使用 Webpack，无此限制
  - 功能完全满足需求，稳定性更高
- **风险**: 低
- **可回滚**: 是（升级回 16 需要将项目移至英文路径）
